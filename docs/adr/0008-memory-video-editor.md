# Memory video editor

Keep the existing authenticated synchronous renderer. Peak demand is unknown; the existing per-customer lock and two concurrent renders per process remain the admission boundary. Each request carries 1–15 photos (at most 10.5 MB base64) and optionally 3 MB audio (4 MB base64), within an 18 MiB render-only JSON limit. Other API limits stay unchanged. No persistent server data: inputs, scenes and output live in a request-owned temporary directory. Retained server volume remains zero at 12/36 months; growth affects compute concurrency. Worst-case admitted throughput is two renders per 85 seconds per process; sustained demand beyond this needs a separately designed queue.

Add defaulted editing options to the existing request and authenticated capabilities so older renderers cannot silently ignore options. Themes: postcard, cinema, journal. Opening: custom caption or trip title/year. All photos appear in order, with gentle motion/fades and an ending, within exactly 60 or 90 seconds. Sound: silence, original CC0 procedural instrumentals, or selected MP3/WAV/M4A/AAC. Uploaded audio is limited to 3 MB, signature checked, decoded with format/protocol allowlists, and trimmed/faded to the film. Rasterise user text; never interpolate it into FFmpeg expressions or shell commands.

Assets are private photos/audio. Threat actors are malicious request metadata and another customer's requests. Local reads/deletes require the current account, trip and exact generated filename. Server identity comes from verified auth and existing per-customer admission control. No input/token logging. Discard removes only the generated preview after playback releases it; source photos and exported external copies remain.

Keep the 85-second render deadline, 90-second route and 125-second client timeouts. Availability follows the existing API; no new measured SLO. Verify real FFmpeg with 1/15 images, exact frames/duration and audio inspection. Decoder/render failures produce recoverable errors, without automatic retry or external publishing. Bound compute with thread limits and admission control; measure worst-case runtime. No third-party music download, new database or job queue. Compared with remote music libraries, original CC0 music avoids licensing ambiguity and availability dependencies.

Deploy additive backend first; capabilities gate mobile options. Rollback preserves legacy silent requests and disables unsupported editor options. No migration. Audio selection needs a new binary with expo-document-picker. Production rollout needs explicit approval once build and release target are reviewable.
