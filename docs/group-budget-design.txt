Roamie shared group expenses — implementation decision, 21 October 2026
Assumed initial scale: 1,000 groups/year × 280 expenses = 280k expense rows at 12 months; 10,000 groups/year = ~2.8m at 36 months. Peak 10 mutations/s, 100 reads/s; typical payload <16 KB, bounded group response <2 MB. Target p99 <500ms for warm ledger reads, 99.9% API availability. FX lookup can be slower and is outside a database lock. These are design assumptions, not measured traffic.
Use existing modular Rust API, Postgres group tables and authenticated customer boundary. Add contacts, persisted split method, settlement records, optimistic group revision and deduplicated commands through an additive migration. No new service/provider or open-source web application deployment. Spliit and SplitPro are useful MIT-licensed product references; no third-party source is copied.
All group writes lock the group row, verify active membership and operation permission, validate expected revision, enforce command-id/hash replay, and commit changes + audit atomically. Reads acquire a shared group lock for a consistent bounded snapshot. The client refreshes after writes and on foreground, uses request timeouts, and does not claim an unsuccessful write succeeded. Participant contacts are visible to members; only the owner or the participant themselves can change their contact details. The owner explicitly enables an email invitation for an existing unclaimed participant for seven days. A verified customer must match that invited email to join. Sharing a group ID alone never grants access. Contacts alone do not authorize membership.
Equal default, percentages in integer basis points totalling 10,000, or exact original-currency minor amounts totalling the original amount. Allocate residual minor units deterministically using largest remainders. Expenses and settlements are separate events. Calculate direct pair debts by currency, net reciprocal expenses, apply repayments FIFO to oldest obligations and never mix currencies. Editing/removing expenses keeps real repayment history and shows any resulting overpayment as an amount owed back. New settlements cannot exceed the current debt.
Original currency is authoritative. Every member sees current home-currency reference estimates from the existing FX endpoint and an at-entry home conversion stored with each expense for its creator. The current provider supplies daily reference rates, cached 6h, not tick/live quotes; timestamp and unavailable states must be visible. Currency minor-unit precision must follow ISO 4217 consistently. Automatic conversion is a calculation, not a money transfer.
Reminder preference was not selected: assume an overdue prompt and user-reviewed email/WhatsApp compose actions after 30 days of unpaid obligation. Track outstanding oldest dated debt after repayments, rather than reminder age from the latest expense. No automatic 30-day scheduler or business messaging credentials are used. Explicitly requested email reminders use a Postgres outbox and server-only Resend sender; WhatsApp remains a reviewable share action. Do not mark compose/open as delivery confirmation.
Threat model: group balances, contacts, invitation tokens and settlement history are sensitive. Unauthenticated callers and other groups must not read/change objects; membership and permission are checked in SQL, unknown groups/invites return 404, membership follows only an explicit unexpired invitation matched to the verified customer email, and actor is derived from verified auth. Tokens/contacts/financial payloads never enter logs. Use no-store responses and existing bounded body/timeouts. Mobile cache cannot cross accounts. Third-party contact app handoff occurs only on an explicit user action.
Validation: red then green split/rounding/currency/age tests; native component form/edit/settlement/reminder controls; real scratch Postgres migration, permission, replay/concurrency, unauthorized membership and lifecycle tests; full Rust/mobile checks; iOS simulator verification and Android export/device availability. Production migrations or rollout require separate named approval after implementation is reviewable.

Email delivery: request and idempotent command commit atomically. The relay claims a 90-second lease, rechecks current membership, contact and overdue balance, and uses a stable Resend idempotency key. Five bounded retries with jitter remain within 23 hours, inside the documented 24-hour provider dedupe window. Account and recipient advisory locks enforce 20 requests/account/day and 5/recipient/day; the same debt has a seven-day pending/accepted cooldown. Status accepted means provider acceptance, not delivery. If the contact or balance changes, further attempts are cancelled. There is an unavoidable external-send race with simultaneous settlement; reminder text describes the balance at request time and asks recipients to check the current ledger.
Database rollback: both migrations are additive. Roll back the API/mobile feature and disable the sender if necessary while retaining new columns/tables and audit history. Do not drop customer records as an automatic rollback.
