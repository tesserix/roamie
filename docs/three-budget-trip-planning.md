# Reviewed trip planning

A traveller supplies destination(s), dates, party, preferences and an optional spending ceiling in the existing trip form. The trip manager loads their API-owned profile, allows preference edits, and saves with an expected revision before requesting advice. The API replaces the client reference with the authenticated customer's saved snapshot. No mobile workload token or provider key is used.

The existing signed manager → A2A trip specialist path produces exactly three options: budget, balanced and premium. The ADK specialist calls models through Agent Gateway. The manager checks proposed intent, then independently checks the returned plan against the profile and source facts before final model review. Dates, destination/day allocations, place references, chronological stops, accommodation provenance and ascending whole-party budgets are validated in code. A failed or unavailable provider never becomes three fabricated options.

Budgets are approximate allocations for accommodation, food, activities, local transport and contingency, not provider quotations; international flights are excluded. Hotel listings are suggestions to compare, not verified room availability. Suggested stop times are not verified opening hours. Restaurant dietary/allergen claims still require source evidence. All these distinctions must remain visible in the app.

The app compares all three plans, checks the profile revision again on selection, and stores the chosen option with sources and review identity in account-scoped trip storage. No booking or payment happens. Specialist follow-ups use the same manager API. The legacy unreviewed planner is no longer used by the trip screen.

Contracts: `apps/mobile/src/lib/planning-contract.ts` is generated by ai-agents `scripts/export_roamie_mobile_contract.py`; the MCP input/output artifact is generated by `scripts/export_roamie_contract.py`. Both are shipped with registry 1.1.0. The registry discovery pin must match the new graph and immutable deployed images.

Release order: publish API and MCP images; publish agent images; update catalog pins and the publisher's reviewed Roamie revision; publish/verify the 1.1.0 graph; deploy matching API/MCP/agents and gateway timeouts through GitOps; exercise a signed-in saved-profile flow; only then activate the customer bridge and produce the mobile preview build. These source changes alone do not enable the currently disabled production bridge.

## Validation-only release

The API defaults `TRIP_MANAGER_CUSTOMER_ENABLED` to false even when manager credentials are configured. In that mode `/v1/trip-manager` additionally requires `X-Roamie-Validation-Authorization: Bearer <manager API key>`. It still requires the ordinary authenticated customer bearer, server-owned saved profile, current revision and both manager reviews. Never put the operator credential in the mobile app. This permits an operator-only end-to-end check before enabling ordinary customer requests.

API requests finish within a 90-second route deadline (below the documented 100-second origin limit); the app cancels at 95 seconds. An unavailable or timed-out planning request is shown as a failure, not a partial three-option comparison.
